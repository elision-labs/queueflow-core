# QueueFlow on Render

`render.yaml` at the repository root is a Render Blueprint that creates:

- a Render Postgres instance `queueflow-db` (PostgreSQL 16), and
- a web service `queueflow` running the prebuilt image
  `ghcr.io/elision-labs/queueflow:0.2` in `--mode all`, with `/health` as the
  health check.

Field names were checked against the Blueprint spec
(<https://render.com/docs/blueprint-spec>) and its JSON schema
(<https://render.com/schema/render.yaml.json>).

## Deploy

1. Push a repository that contains `render.yaml` at its root (a fork of this
   one, or a one-file repo with a copy of it).
2. Render Dashboard: **New** -> **Blueprint**, pick that repository and branch.
3. Render shows the resources it will create and prompts for every variable
   marked `sync: false`. Enter:
   - `QUEUEFLOW_API_KEYS`: one or more `token:tenant` pairs, comma-separated,
     for example `$(openssl rand -hex 24):acme`.
4. Apply. `QUEUEFLOW_WORKER_TOKEN` is generated by Render
   (`generateValue: true`, a random 256-bit value) and `DATABASE_URL` is wired
   from the database (`fromDatabase: connectionString`, the internal
   connection string).
5. When the service is live:

   ```bash
   curl -s https://<service>.onrender.com/health
   curl -s https://<service>.onrender.com/ready
   ```

To read the generated worker token for your workers: service -> **Environment**
in the Dashboard.

## What the Blueprint sets and why

| Key | Value | Why |
| --- | --- | --- |
| `runtime: image`, `image.url` | `ghcr.io/elision-labs/queueflow:0.2` | Prebuilt, public image; no build. Pin to `0.2.0` for an exact version. |
| `healthCheckPath` | `/health` | 200 only when the process can reach Postgres. No token needed. |
| `PORT`, `QUEUEFLOW_API_PORT` | `8000` | Render routes traffic to the port in `PORT`; QueueFlow listens on `QUEUEFLOW_API_PORT`. Both pinned so they agree. |
| `QUEUEFLOW_MODE` | `all` | API + in-process workers + janitor + cron in one process. |
| `DATABASE_URL` | `fromDatabase` | Internal connection string of `queueflow-db`. |
| `QUEUEFLOW_API_KEYS` | `sync: false` | Secret; prompted once at creation, never in Git. |
| `QUEUEFLOW_WORKER_TOKEN` | `generateValue: true` | Secret; random value created by Render. |
| `autoDeployTrigger: off` | | The service is image-based; redeploy explicitly when you bump the tag. |
| `plan` | `starter` / `basic-256mb` | Smallest always-on tiers. Do not use `free` for the web service: it spins down when idle, which stops workers, cron and the janitor. |

Values are strings or numbers in a Blueprint; the schema allows both for
`value`.

## Limits to know

- Render exposes one HTTP port per web service. Prometheus metrics on 9090
  are therefore not reachable from outside. Use the database for fleet-wide
  numbers (see the deployment guide at <https://docs.queueflow.dev/deployment>).
- Migrations run on server startup (`--auto-migrate` defaults to true). To
  run them as a separate step instead, add a Render Job or use the
  **Shell** tab: `queueflow migrate` with `DATABASE_URL` set, and set
  `QUEUEFLOW_AUTO_MIGRATE=false` on the web service.
- Set `QUEUEFLOW_CORS_ORIGINS` if browsers call the API directly; otherwise
  CORS is permissive and the server logs a warning at startup.
- `sync: false` values are prompted only on first creation; later Blueprint
  syncs leave them untouched. Rotate them in the Dashboard.

## Split topology

For separate API and worker services, add a `type: worker` service with the
same image and `QUEUEFLOW_MODE=worker` (no HTTP, so it needs only
`DATABASE_URL`), and set the web service to `QUEUEFLOW_MODE=api`. Remote
workers written against the SDKs connect to the web service URL with the
worker token.
